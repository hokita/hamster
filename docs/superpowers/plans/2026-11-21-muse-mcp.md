# Muse connection (MCP server) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the owner's agent Muse find, open, save, mark read and summarize hamster bookmarks through an MCP server at `/mcp` in `hamster-backend`.

**Architecture:** This copies owlet's pattern: a stateless streamable-HTTP MCP server mounted with `app.all('/mcp', apiTokenAuth, handler)`, a bearer token from Secret Manager, and an in-memory per-tool-call limiter. Summary generation moves out of `routes/bookmarks.ts` into a shared generator so the app and Muse join the same run. A Firestore-backed counter caps summaries started through Muse at 10 an hour.

**Tech Stack:** Node 24.22.3, Express 4, TypeScript, vitest + supertest, `@modelcontextprotocol/server` 2.4.0, `@modelcontextprotocol/node` 2.1.2, `zod` 4.6.7, dev `@modelcontextprotocol/client` 2.4.0, Firestore (Admin SDK), Playwright e2e with the emulators, gcloud and gh.

**Spec:** `docs/superpowers/specs/2026-11-21-muse-mcp-design.md`

## Global Constraints

- Exactly five tools: `find_bookmarks`, `open_bookmark`, `save_link`, `set_read`, `summarize_bookmark`. No chat, translate or delete.
- Token env var `HAMSTER_MCP_TOKEN`, secret `hamster-mcp-token`, repo variable `HAMSTER_MCP_TOKEN_SECRET`; minimum length 43; unset turns `/mcp` off (everything gets 401).
- `/api/bookmarks` keeps `authMiddleware` only: the MCP token must get 401 there.
- Limits: 60 MCP tool calls an hour (in memory, per instance); 10 summaries started through Muse an hour (Firestore, global). Protocol requests aren't counted.
- Summary wait: 45 000 ms, then "Still summarizing…" (not an error); the run keeps going.
- Find: `limit` 1–50, default 20; `query` ≤ 200 chars. Transcript in `open_bookmark` cut at 100 000 chars.
- Bookmark id pattern `/^[A-Za-z0-9_-]{1,64}$/`; URL must be `http(s)://` and ≤ 2048 chars.
- Never commit, log or print a real token, API key or the owner's email. The fixed e2e token in `backend/.env.e2e` is a fake for the emulator only.
- Don't install anything outside the worktree, and don't kill processes you didn't start. If an e2e port clash happens (8081, 9099, 8090, 5174), report it.
- No GitHub comments and no merge. Merging to main deploys to production.

## Review Focus

1. **Token stored with a trailing newline.** `openssl rand -hex 32` ends in `\n`, so a secret piped in unchanged would never match the header and every call would get 401. The pipe strips it with `tr -d '\n'`, and the matcher trims the configured value too (Task 1 test `ignores surrounding whitespace in the configured token`).
2. **Ids that don't exist or aren't ids.** `''`, `'a/b'`, `'../x'` or 200 characters → tool error `Invalid bookmark id`, and Firestore is never called. A well-formed unknown id → `No bookmark with id <id>` (Task 4 tests, reused by every tool that takes an id).
3. **Japanese and full-width text.** `ＡＩ` finds `AI`, a full-width space `　` separates words, and `要約` matches inside a Japanese summary (Task 4 test `matches Japanese and full-width text`).
4. **Concurrent calls.** Two `summarize_bookmark` calls for one id → one Gemini run and one budget slot. A Muse summarize while the app's Generate is running joins it. Two simultaneous `save_link` calls for one URL → one bookmark (Task 5 and Task 6 tests).
5. **Huge results.** 500 bookmarks with long summaries → one page of at most 50 items with no full summaries. A 3-hour transcript → cut at 100 000 chars with `transcriptTruncated: true` (Task 4 tests).

Token rotation (adding a new secret version and redeploying) is in the README task and the deploy smoke check (Task 9). The old token stops working on the first request served by the new revision.
