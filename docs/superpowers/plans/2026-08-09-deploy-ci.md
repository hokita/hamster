# Deploy & CI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Tasks 1-7 are ordinary SDD tasks. The final "Manual Deployment & Go-Live" section is explicitly NOT an SDD task — it touches real production infrastructure and must be run directly by (or with) the human partner, not dispatched to a subagent.

**Goal:** Deploy hamster to real infrastructure (Firebase Hosting + Cloud Run) with GitHub Actions CI/CD via Workload Identity Federation, and close the `email_verified` gap in `authMiddleware` before the app is reachable from the real internet.

**Architecture:** Backend deploys as a Docker container to Cloud Run via a two-stage Alpine build; frontend builds and deploys static assets to Firebase Hosting. Four GitHub Actions workflows: `ci.yml` (lint/typecheck/test/e2e on every PR), `backend.yml`/`frontend.yml`/`firestore-rules.yml` (deploy on push to `main`, path-filtered). All deploy workflows authenticate via WIF — no static GCP credentials anywhere.

**Tech Stack:** Docker, Cloud Run, Firebase Hosting, GitHub Actions, Workload Identity Federation, `google-github-actions/auth`.

**Related spec:** `docs/superpowers/specs/2026-08-09-deploy-ci-design.md`

## Global Constraints

- GCP/Firebase project: `hamster-52b093`, region `asia-northeast1` for every resource (Cloud Run, Firestore, Artifact Registry) — already provisioned, see the spec's Infrastructure table for every concrete value (project number, service account email, WIF provider resource name, Firebase web config, etc.).
- `WIF_PROVIDER` and `WIF_SERVICE_ACCOUNT` are already set as GitHub repo secrets on `hokita/hamster` — do not recreate them.
- `ALLOWED_EMAILS` secret already exists in Secret Manager — do not recreate it.
- Firebase's client-side web config (`apiKey`, `authDomain`, `projectId`) is public-facing by design — it goes directly as plain values in workflow YAML, not GitHub secrets. This matches corgi's approach and is not a security issue: access control is Firestore rules + backend auth, not hiding these values.
- Cloud Run: `--allow-unauthenticated` (the app's own `authMiddleware` is the access-control layer, not Cloud Run IAM), `--min-instances 0 --max-instances 2`.
- The `email_verified` check must be identical in every environment — no env-conditional branch in `authMiddleware`. Environments that need an unverified-by-default test user (e2e) must make that user verified via setup code instead, not by weakening the check itself.
- Node 24 throughout, matching the existing backend/frontend `package.json` engines.

- [ ] **Step 3: Implement the check**

Modify `backend/src/middleware/auth.ts`:

```ts
import type { Request, Response, NextFunction } from 'express'
import { getAuth } from 'firebase-admin/auth'

function allowedEmails(): Set<string> {
  return new Set(
    (process.env.ALLOWED_EMAILS ?? '')
      .split(',')
      .map((email) => email.trim().toLowerCase())
      .filter(Boolean)
  )
}

export async function authMiddleware(
  req: Request,
  res: Response,
  next: NextFunction
): Promise<void> {
  const token = req.headers.authorization?.split('Bearer ')[1]
  if (!token) {
    res.status(401).json({ error: 'Missing token' })
    return
  }
  try {
    const decoded = await getAuth().verifyIdToken(token)
    if (
      !decoded.email ||
      !decoded.email_verified ||
      !allowedEmails().has(decoded.email.toLowerCase())
    ) {
      res.status(401).json({ error: 'Unauthorized' })
      return
    }
    next()
  } catch {
    res.status(401).json({ error: 'Invalid token' })
  }
}
```

- [ ] **Step 5: Fix the e2e test user to be email-verified**

Modify `e2e/global-setup.ts`:

```ts
import { AUTH_EMULATOR_URL, TEST_EMAIL, TEST_PASSWORD } from './fixtures/auth'

async function waitUntilListening(url: string, attempts = 20, delayMs = 500) {
  for (let i = 0; i < attempts; i++) {
    try {
      await fetch(url)
      return
    } catch {
      await new Promise((resolve) => setTimeout(resolve, delayMs))
    }
  }
  throw new Error(`Timed out waiting for ${url} to accept connections`)
}

export default async function globalSetup() {
  await waitUntilListening(AUTH_EMULATOR_URL)

  let idToken: string | undefined
  try {
    const res = await fetch(
      `${AUTH_EMULATOR_URL}/identitytoolkit.googleapis.com/v1/accounts:signUp?key=fake-api-key`,
      {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ email: TEST_EMAIL, password: TEST_PASSWORD, returnSecureToken: true }),
      }
    )
    const data = (await res.json()) as { idToken?: string }
    idToken = data.idToken
  } catch {
    // User already exists from a prior run against this emulator session —
    // it was already marked verified the first time, so there's nothing to do.
  }

  if (!idToken) return

  await fetch(
    `${AUTH_EMULATOR_URL}/identitytoolkit.googleapis.com/v1/accounts:update?key=fake-api-key`,
    {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ idToken, emailVerified: true }),
    }
  ).catch(() => {})
}
```

This mirrors how a real Google sign-in behaves (always pre-verified) rather than adding an environment-conditional branch to `authMiddleware` itself.

          gcloud run deploy hamster-backend \
            --image asia-northeast1-docker.pkg.dev/hamster-52b093/hamster/backend:latest \

            --allow-unauthenticated \
