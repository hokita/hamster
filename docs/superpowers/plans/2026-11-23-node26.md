# Node 26 LTS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run hamster on Node 26.13.1 everywhere it runs on Node: the Cloud Run backend image, every CI and deploy workflow, and every local pin.

**Architecture:** This is a version move with no product code change. The backend image's pinned `FROM` lines decide the production Node. `actions/setup-node` decides the Node used by CI, deploys and the nightly audit. Volta decides the local Node. A new `node:test` file asserts that all of these agree, and it runs in the existing `Actions pinned` job.

**Tech Stack:** Node 26.13.1 (LTS "Lithium", npm 11.20.0), `node:26.13.1-alpine` (alpine 3.23), GitHub Actions, Volta, firebase-tools 15.37.0, Cloud Run, Firebase Hosting.

**Spec:** the task brief from 2026-11-23 and the survey at `/tmp/node26-survey/REPORT.md`, §0 and §2.5. The brief named `hamsterRT.md`, but that file does not exist; `REPORT.md` is the only file in that directory.

## Node 25/26 breaking changes checked against this repo

Moving from 24 to 26 crosses the semver-majors of both 25 and 26. I read them from `CHANGELOG_V25.md` and `CHANGELOG_V26.md` on nodejs/node main and grepped the repo's own code (`backend/src`, `backend/scripts`, `.github/scripts`, `e2e`) for each one:

| Change | Hits in hamster | Effect |
|---|---|---|
| `writeHeader`, `_stream_*`, `SlowBuffer`, `fs.F_OK`…, `module.register`, `--experimental-transform-types`, `util.isX`, `url.parse` | none | none |
| Undici 8 behind global `fetch` | `backend/src/services/safeFetch.ts:49` (`redirect: 'manual'` loop), `@google/genai` and the e2e fixtures | **Main risk.** The redirect, `location` header and abort handling for title, favicon, article and YouTube fetches. The unit tests mock `fetch`, so Task 4 checks the real network once. |
| `dns.lookup` with a falsy hostname is now end-of-life (throws) | `safeFetch.ts:23` | The `try/catch` already turns a throw into "disallowed", so the behaviour is fail-closed. No change needed. |
| Web Storage (`localStorage`) on by default; in 26 it returns `undefined` without a file | the frontend tests run in vitest + jsdom | Could shadow jsdom's storage. The frontend `src` doesn't use `localStorage` (grep shows none), but Firebase Auth's browser SDK might. The frontend test run on 26 settles it. |
| `NODE_MODULE_VERSION` 147 | no native addons in the backend image. `re2` 1.26.1 (optional, via firebase-tools) supports `>=26.0.0`. esbuild and tailwind oxide ship per-platform binaries. | low |
| Extensionless-CJS exception removed for `"type":"module"` packages | `frontend` is `type: module` but has no extensionless entry points | low; the build covers it |

## Review Focus

1. The deploy runs on 26 but the deployed revision is still on 24 (a failed deploy, or traffic pinned to an old revision). The nightly would then say "Production runs v24.22.3; no newer Node 24 security release" and pass. The post-merge checks below compare the deployed `node --version` directly with `v26.13.1`.
2. Undici 8 redirects: a 301/302 chain with a relative `Location` must still resolve, and each hop must still go through `isDisallowedHost`. This is covered by the existing `safeFetch.test.ts` on 26 plus the live check in Task 4.
3. `npm ci` in the final image: npm's location in the 26 alpine image must match the `rm -rf` paths at `Dockerfile:15`, or npm ships again (a regression of #42). Task 4 checks that `npm` and `npx` are gone from the built image.
4. A Dependabot docker PR that bumps only the Dockerfile to a newer 26.x will now fail `node-pins.test.mjs` until setup-node and Volta are bumped with it. That is intended, because it forces one coordinated bump.
5. `superstatic` `EBADENGINE` warnings during `npm ci` in the root and e2e are expected and non-fatal. Any other `EBADENGINE` is a finding.

## Deploy on merge, and how to verify it

Merging to main triggers these workflows, through their `paths` filters:

| Workflow | Why it runs | What it does |
|---|---|---|
| `Deploy Backend` (`backend.yml`) | `backend/**` and `.github/workflows/backend.yml` changed | lint, test and build on 26, then builds and pushes the 26 image and runs `gcloud run deploy hamster-backend` |
| `Deploy Frontend` (`frontend.yml`) | `frontend/package.json` and `frontend.yml` changed | lint, test and build on 26, then Hosting deploy with firebase-tools 15.37.0 |
| `Deploy Firestore Rules and Indexes` (`firestore-rules.yml`) | its own file changed | redeploys the unchanged rules and indexes on 26 with firebase-tools 15.37.0. The content is the same, so it's harmless. |

After merge:
1. `gh run list --branch main --limit 5`: all three runs succeed.
2. `curl -fsS <backend URL>/health` → 200, and the frontend URL loads and sign-in works (manual).
3. Production Node: dispatch `Audit (nightly)` (`gh workflow run audit-nightly.yml`, with the user's OK) and expect the `Deployed image (backend)` job to print `Production runs v26.13.1; no newer Node 26 security release.` This job reads `node --version` from the image digest of the latest ready revision, so it shows what is actually deployed. A `v24.22.3` here means the deploy didn't take (Review Focus 1).
4. Watch the Cloud Run logs of the new revision for `DeprecationWarning` and for errors in title, favicon or summary fetches during the first real bookmark save.
5. Rollback: either revert the PR (this redeploys the 24 image through `backend.yml`), or move the traffic straight back with `gcloud run services update-traffic hamster-backend --region asia-northeast1 --to-revisions <previous revision>=100`.
